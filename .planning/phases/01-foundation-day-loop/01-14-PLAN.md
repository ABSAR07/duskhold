## Owner Decision vs Design Defaults

Binding (owner, UAT G-01-58, amends D-05): the first coin takes 0.25 s; later coins accelerate; a whole hold never exceeds 3 s; at 3 s every remaining coin is paid at once and the build completes, provided the gold covers it. That proviso is always true today: a hold only starts when `validate_build` passes the full-cost check (D-06, `simulation/commands/command_processor.gd` lines 30-40), gold is debited once at completion, and nothing else changes gold during a day hold. If a later phase ever lets gold drop mid-hold, the completion submit already returns CANNOT_AFFORD and the controller emits `hold_cancelled` with a full refund. A partial "stop at what is affordable" path would create the partially-paid state D-06 forbids, so it is not built.

Non-binding parameters (from `.planning/debug/build-hold-pacing-curve.md`, adopted as defaults; all live in data per D-09 and are retuned at the Phase 2 playtest):

| Field | Default | Why |
|-------|---------|-----|
| `coin_drip_interval` (first and steady interval) | 0.25 s | Owner value; inside D-05's documented 0.15-0.3 s range; the name is kept so existing overrides still compile |
| `coin_drip_steady_coins` | 2 | Keeps House I at exactly 0.5 s, the UAT G-01-4 minimum. Decaying from coin 2 instead would make House I 0.475 s and break that contract |
| `coin_drip_decay` | 0.90 | Each later coin takes 90% of the previous one. A steeper 0.85 lets 30 coins finish naturally under 3 s with almost no fast-forward |
| `coin_drip_min_interval` | 0.08 s | Floor so a long hold's stream stays readable (reached at coin 13) |
| `max_build_hold_seconds` | 3.0 s | Owner value |

Resulting holds: cost 2: 0.500 s, 3: 0.725, 4: 0.9275, 5: 1.110, 6: 1.274, 10: 1.781, 15: 2.205, 30: 3.000 (24 coins drip, 6 fast-forwarded; 3.405 s uncapped), 50: 3.000 (24 drip, 26 fast-forwarded, about half, as in the owner's example). Today (linear 0.3 s): 0.6 / 0.9 / 1.2 / 1.5 / 1.8 / 3.0 / 4.5 / 9.0 s.
