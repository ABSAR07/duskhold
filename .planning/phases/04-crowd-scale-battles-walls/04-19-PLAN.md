<exact_port_rules>
Restated in every port plan (04-15 to 04-20, 04-23):
1. Vector2 is godot::Vector2 with real_t float (precision single). Every GDScript float (scalars, radii, ranges, speeds, a method result once it leaves the method, PackedFloat64Array elements) is double in C++; GDScript int is int64_t.
2. Narrow exactly where GDScript narrows: a scalar meeting a Vector2 (v * s, v / s, s * v, move_toward's delta, lerp's weight, a PackedFloat32Array store, Vector2(x, y) built from doubles) is cast to real_t at that operator; a Vector2 method result (length, distance_to, dot, cross, .x, .y) is widened to double as it leaves. Keep each expression's operation order and grouping; never reassociate or hoist a subexpression that changes rounding.
3. GDScript utilities and Vector2 methods only as native/src/gd_math.h's table allows (plan 04-15 proved each bit-equal to the engine).
4. Ascending id or index order everywhere, ties broken exactly as the GDScript does (a strict < keeps the earlier); no unordered containers; any sort ends with the id.
5. Candidate sets equal the GDScript's wherever membership or order can change an answer; a superset is allowed only where the code takes a strict minimum over an exact test.
6. No FMA and no fast math (/fp:precise, -ffp-contract=off, no AVX or host-tuned switch); only + - * / and sqrt; test_native_rules_guard enforces it.
7. Pins first: the GDScript step's behaviour is pinned before it is replaced; here the pins are the four goldens, the gate digest and the per-tick traces of tools/stress/enemy_trace.gd taken from the unchanged GDScript at the start of Task 1.

<step_contract>
What the GDScript EnemySystem.step does today, which the native pair must reproduce (enemy_system.gd as left by plan 04-12):
- Order: previous := position for every record; return if the castle is destroyed; StructureIndex.rebuild (the facade still calls it: it gathers units, buildings and the castle); when walls are solid, _publish_wall_times (begin_tick, add_attacker per living record with wall_seg on an intact segment, else wall_seg := -1, end_tick); for each living record in ascending id: _choose_target then _advance_and_strike; then _separate (living records, Separation.displacements_bucketed with cell 2 * largest radius + 0.001); then, when walls are solid, push_out of every living record whose def does not ignore walls.
- Within the per-enemy loop no enemy reads another enemy's state and nothing reads the hit queue; strikes only enqueue and emit. So the native loop collects strikes as (arrival tick, attacker id, target kind code, target id, damage, flight ticks) in id order, and the facade enqueues each and emits attack_fired for it right after the loop and before the push-apart call, which keeps the recorded event order and every listener's view of the attacker's position.
- Inputs fixed for the whole enemy phase (nothing moves or falls before hits resolve, DR-8): the castle (position, radius, destroyed), the king (up, position, body radius; none when null), the living units and standing buildings (in NativeStructures since 04-18), the walls (NativeWalls), the castle route and field (NativeRoute), the decision (NativeWallDecision), the tick, whether walls are solid.
- Per-def numbers are read live in GDScript, so the facade refreshes the native def table from each registered EnemyDef at the start of every step (a handful of defs), never only at first spawn; spawn-time caches (rescan_ticks, per_300, speed_cm, health) stay per record as today.
- Kinds cross as small integers (none, king, unit, building, castle, wall) mapped to PendingHits.KIND_* in the facade; a killer kind is any StringName (the gate sink uses its own), so the facade keeps killers in a Dictionary by id.
- EnemySystem.desired_step and is_rescan_tick stay GDScript statics (squads, Pathing and tests call them); the native step uses their C++ twins (move_toward is in the 04-15 contract).
</step_contract>
