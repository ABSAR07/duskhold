Restated in every view-port plan (04-25 to 04-27):
1. Vector2 and Vector3 are godot-cpp types with real_t float; Color components are float; PackedFloat32Array elements are float. Every GDScript float (blend, the bar height constant sum, the bar ratio, a method result once it leaves the method) is double in C++; GDScript int is int64_t.
2. Narrow exactly where GDScript narrows: the lerp weight is cast to real_t; `origin + Vector3.UP * (PUPPET_HEIGHT + BAR_CLEARANCE)` adds the two constants in double, narrows the sum at the multiply, multiplies Vector3(0, 1, 0) by it and adds the result to the origin with godot-cpp's Vector3 operators (proven in plan 04-25); the bar ratio is a double narrowed into the custom Color. Keep every expression's operation order and grouping.
3. Vector math only through native/src/gd_math.h as its operation table allows.
4. Visit order is the GDScript's: ascending unit id (the read view's order is UnitSystem's id order, which the GDScript loop walked).
5. The mirror: write exactly CrowdBatch.add's floats (the origin; the type batches have no colours; the custom data) in the same places; the floats past the count keep what earlier frames left; the native fill starts from each batch's setup mirror.
6. No FMA and no fast math; only + - * / and sqrt; no time, no randomness, no engine singleton in native/src; test_native_rules_guard enforces it.
7. Pins first, on the GDScript, committed on their own, never edited.
8. One implementation ships: the replaced GDScript per-frame body is deleted; no runtime fallback.

10. Every native method checks sizes, batch indices and ids that cross from GDScript and answers what the GDScript answered for bad input.
11. GDScript names native classes as types (rule (i) of 04-14-SUMMARY).
12. Constants stay GDScript and are handed over at bind; the one rule copied into C++ is HealthBar3D.should_show (max_hp > 0 and hp > 0 and hp < max_hp), with its source named.
